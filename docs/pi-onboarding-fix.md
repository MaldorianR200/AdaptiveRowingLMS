# Исправление экрана входа и завершение обновления дизайна

Передай этот документ Pi вместе с `docs/pi-redesign-task.md`. Он описывает текущее состояние после появления двухшагового входа. Скриншот пользователя показывает дефект на первом шаге: два логотипа/шапки, почти неоформленную форму и большой пустой участок до подвала. Не ограничивайся изменением текста или одного цвета — доведи весь сценарий и дизайн до готового состояния.

## Установленные причины

1. `src/app/features/onboarding/onboarding-page.html` использует классы `onboarding-shell`, `onboarding-visual`, `onboarding-form-panel`, `stepper`, `field`, `role-option` и другие, но соответствующих правил нет ни в `src/styles.scss`, ни в отдельном SCSS. В `onboarding-page.ts` отсутствует `styleUrl`. Поэтому браузер показывает поля, подписи и шаги почти в стандартном виде, а запланированная двухколоночная композиция не работает.
2. `src/app/app.html` безусловно выводит `<app-header />`, `<main><router-outlet /></main>` и `<app-footer />` для **всех** маршрутов. Страница входа внутри содержит ещё один `<main>` и собственный логотип. Это создаёт две шапки, два `main` landmark и лишний подвал на экране входа.
3. Глобальное правило `main` в `src/styles.scss` задаёт ширину и отступы всем элементам `main`, включая вложенный `main.onboarding-shell`. Даже после добавления стилей оно может продолжать сжимать или смещать приветствие. Раздели стили оболочки приложения и экрана входа по явным классам.
4. `src/app/shared/components/app-header/app-header.html` выводит пустой `.brand-mark` с пустым внутренним `span`; для него нет реализации рисунка. На скриншоте вместо знака виден пустой светлый квадрат. В приветствии другой вариант логотипа — буквы `AR`. Нужен единый знак, согласованный с favicon.
5. Дизайн остальных страниц всё ещё в основном основан на старом глобальном `src/styles.scss`: белые карточки, простая шапка, прежняя типографика. Новые формулировки на страницах не равны требуемому кардинальному обновлению дизайна.

## Что исправить в первую очередь

### 1. Разделить оболочки маршрутов

- Сделай корневой `App` точкой размещения маршрутов. Для обычных страниц создай компонент `AppLayout` с шапкой, одним `main` и подвалом. `/onboarding` должен рендериться вне этого layout, даже если в браузере уже есть активный профиль и пользователь нажал «Добавить пользователя».
- Guard на внутренних маршрутах должен перенаправлять на вход до отображения приватной оболочки. Не допускай краткого появления навигации при первом открытии.
- На любом маршруте должен быть один главный `<main>`. Страница входа показывает один бренд; внутренние страницы — общую шапку.
- Не решай проблему простым `*ngIf="!hasProfile"` вокруг шапки: при добавлении второго пользователя активный профиль ещё существует, и двойная шапка повторится. Разделение должно зависеть от маршрута/layout.

### 2. Реализовать полноценные стили входа

- Добавь `onboarding-page.scss` и подключи его через `styleUrl` либо используй согласованную систему стилей проекта. Все классы из шаблона должны иметь осмысленное оформление. Базовые токены (цвет, типографика, отступы, фокус, состояния) держи в общем месте.
- На широком экране сделай ясную композицию: выразительная информационная область и отдельная форма в хорошо ограниченной колонке. Не растягивай короткую форму на всю ширину и не оставляй огромную пустую область под кнопкой. Центрируй содержимое по доступной высоте с разумными верхним и нижним отступами.
- На узком экране форма должна идти первой по порядку чтения либо визуально располагаться сразу после компактного бренда. Избегай горизонтальной прокрутки при 320–375 px.
- Подписи полей расположи над полями, а не вплотную перед ними. Поля одинаковой ширины, с достаточной высотой, внутренними отступами и видимым фокусом. Ошибка не должна сдвигать соседние элементы неожиданным образом.
- Шаги `01 Профиль` и `02 Роль` оформи как читаемый индикатор с промежутком и явным текущим состоянием. На скриншоте они слиты в одну строку.
- Для карточек ролей нужны выбранное состояние, hover/focus и доступные radio-input. На втором шаге форма должна оставаться визуально целостной и на телефоне.
- Согласуй светлую/тёмную области, логотип, CTA и фон с новым спортивным стилем, описанным в `docs/pi-redesign-task.md`. Не полагайся на внешние шрифты или изображения, которые могут не загрузиться.

### 3. Доработать поведение формы

- Сейчас `role` заранее установлен в `athlete`. Если ожидается осознанный выбор роли, начальное значение должно быть пустым, а переход со второго шага — требовать выбора. Покажи понятную ошибку выбора.
- После неверной отправки сфокусируй первое ошибочное поле; сейчас код только помечает control как touched. Для ошибок поддерживай `aria-invalid`, корректную связь с сообщением и объявление ошибки для экранного диктора.
- Сохраняй введённые имя и фамилию при возврате со второго шага. Проверяй имена после trim, не запрещая обычные имена разных языков, дефис и апостроф.
- После создания профиля открой стартовую страницу соответствующей роли или разрешённую прямую ссылку. Не возвращай нового пользователя на страницу, запрещённую его ролью. Проверь, что `returnUrl` не допускает внешних адресов и `/onboarding`.
- «Добавить пользователя» и «Сменить пользователя» в меню сейчас ведут на одну форму создания. Для смены пользователя добавь выбор существующего локального профиля; для добавления — чистую форму. Не теряй активный профиль до явного выбора, если пользователь отменил действие.

## Остальные проблемы, обнаруженные при проверке

- `src/app/features/materials/materials-page.html` всё ещё скачивает CSV по абсолютному `/assets/documents/training-diary.csv`; при GitHub Pages с base href подпапки путь может вести не туда. Используй адрес, совместимый с base href, и проверь опубликованную сборку.
- `.github/workflows/deploy.yml` запускает `npm test -- --run`; Angular CLI отклоняет `--run`. Замени на поддерживаемую `npm test -- --watch=false` и проверь CI.
- `src/app/app.spec.ts` содержит всего три теста и не проверяет вход, layout, выбор роли и визуальные состояния. Добавь тесты для первого входа, возврата, второго шага, ошибок, роли, профиля и переходов. Отдельно проверь, что на `/onboarding` нет общей шапки и подвала.
- Убедись, что дизайн остальных маршрутов действительно обновлён: спортсмен, тренер, ассистент, курс, лекция, тест, результат, материалы, форум и доступность. Не оставляй смесь нового приветствия и старых страниц.
- Проверь роль ассистента и сам сценарий теста после нового входа. Клиентские роли остаются демонстрационными; тексты интерфейса не должны обещать защищённую авторизацию.

## Критерии приёмки

1. На `/onboarding` на скриншоте видны **один** бренд, **один** главный контент и **нет** общей шапки/подвала. Форма выглядит законченной, без полей браузерного стиля и чрезмерной пустоты.
2. При 320–375, 768 и 1280–1440 px оба шага помещаются и читаются; нет наложений, слипшихся подписей, горизонтальной прокрутки и обрезанных кнопок. Проверь реальные скриншоты на всех трёх диапазонах, а не только успешную компиляцию.
3. Tab, Enter и Space позволяют пройти оба шага. Видимый фокус, ошибки и выбор роли понятны без мыши.
4. Первый вход, повторный вход, добавление и переключение локального профиля работают без смешивания прогресса. Внутренние страницы не показываются до выбора профиля.
5. `npm run lint`, `npm run format:check`, `npm test -- --watch=false` и `npm run build` завершаются успешно. CI использует поддерживаемую команду тестов.

На момент анализа эти команды локально проходят: lint, format:check, build и `npm test -- --watch=false` (3 теста). Это **не** подтверждает корректный внешний вид: проблема на скриншоте не покрыта существующими тестами. Перед исправлениями снова прочитай актуальные файлы и `git status`, поскольку рабочее дерево содержит незакоммиченные изменения.
