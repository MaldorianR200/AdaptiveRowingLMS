# Задание для Pi: новый дизайн и персональный вход в Adaptive Rowing LMS

> Адресат: Pi с Claude Opus 5.5. Выполни задачу в текущем репозитории, а не ограничивайся рекомендациями. Перед изменениями прочитай фактическое состояние файлов и `git status`: рабочее дерево уже содержит незакоммиченный рефакторинг. Не сбрасывай и не перезаписывай чужие изменения. Применяй проектный навык `.pi/skills/angular-frontend/SKILL.md`, если он доступен локально. По завершении покажи изменённые сценарии, результаты проверок и оставшиеся ограничения.

## Контекст проекта

Это клиентская демонстрационная LMS по адаптивной академической гребле на Angular 22, TypeScript, SCSS, Angular Router и localStorage. Backend, регистрация и настоящая авторизация отсутствуют. В исходном документе `docs/source/Системы_дистанционного_обучения.docx` находятся учебный контент и сценарий: четыре страницы лекции, пять вопросов, две попытки и зачёт от 4 из 5 баллов. Сохрани эти правила и честное обозначение ещё не готовых материалов. Роли, введённые пользователем, остаются **демонстрационным выбором**, не выдавай его за защищённый вход или общую базу пользователей.

Папки `src/app/features`, `src/app/core`, `src/app/shared` уже созданы, но рефакторинг не завершён. Проверенный на момент аудита статус: `npm run lint`, `npm run format:check` и `npm run build` проходят; `npm test -- --watch=false` проходит 3 теста. Команда CI `npm test -- --run` падает с `Unknown argument: run`.

Текущий `.gitignore` исключает `/.pi`: навыки Pi, созданные локально в этой папке, доступны на этой машине, но не попадут в репозиторий обычным коммитом. Если работа переносится в другую среду, передай навыки отдельно или согласованно измени способ их хранения.

## Что сейчас не так

### Критично для нового сценария

1. `src/app/core/data/content-data.ts` содержит четыре фиксированные персоны. `src/app/core/state/lms-state.service.ts` сразу выбирает `athlete-anna`; имени и фамилии пользователя никто не спрашивает. `src/app/shared/components/app-header/app-header.html` предлагает переключать готовых людей. Это не соответствует требуемому входу.
2. Идентичность в состоянии привязана к строкам вроде `athlete-anna`, а не к созданному пользователем локальному ID. При простом переименовании демоперсоны прогресс и попытки могут смешаться. Нужна модель локального профиля и миграция существующего состояния.
3. Роль ассистента проходит `roleGuard(['coach', 'assistant'])` и видит те же кнопки сброса результатов и переключения видимости тем, что тренер. Текст страницы обещает только просмотр, но интерфейс это не соблюдает.
4. `setTopicVisible()` сохраняет флаг, но страница курса его не использует. Переключатель в панели тренера визуально работает, а учебный список не меняется.

### Функциональные и архитектурные дефекты

5. `src/app/features/lecture/lecture-page.ts` читает `ActivatedRoute.snapshot` один раз. При переходе между `/course/lecture/:page` Angular может переиспользовать компонент и показать прежнюю страницу. Некорректное значение параметра может привести к отсутствующей `page`. Аналогично проверь динамический `/course/topics/:id`.
6. `/course/quiz/result` открывается без попытки; шаблон показывает пустой результат вместо понятного состояния или перехода. В `QuizPage.submit()` нет повторной проверки лимита попыток и завершения лекции на уровне операции. Для клиентского прототипа это не защита, но UI-сценарий должен оставаться согласованным.
7. Маршрут `/forum/:id` указан, однако страница форума не читает `id` и не открывает конкретную тему. Либо реализуй прямую ссылку на тему, либо убери бессмысленный маршрут.
8. `src/app/features/materials/materials-page.html` предлагает скачать `/assets/documents/safety-guide.pdf`, которого нет. Абсолютные `/assets/...` ломают путь при публикации на GitHub Pages с `base-href` подпапки. Убери неработающую кнопку или добавь реальный файл; используй путь, совместимый с base href.
9. `QuizGraderService` делит результат соответствия на жёстко заданное `3`, а экраны и состояние повторяют числа 4, 5, 2. Сохрани текущие правила, но собери параметры оценивания в одном месте и добавь целевые тесты.
10. `LmsStateService.load()` делает приведение результата `JSON.parse` без проверки структуры. Повреждённый или устаревший localStorage может сломать интерфейс. У `AccessibilityPage` запись в localStorage тоже не обрабатывает ошибку доступа.
11. В нескольких компонентах после разделения остались широкие неиспользуемые импорты. ESLint отключает `@typescript-eslint/no-unused-vars` и `no-explicit-any`, поэтому зелёный линтер не отражает чистоту TypeScript-кода. В `core/models/index.ts` типы переэкспортируются из файла данных — модели стоит отделить от контента.
12. Настройки доступности и внутренний чек-лист проверки объединены на одной пользовательской странице. Пункты чек-листа нельзя считать автоматически выполненными; отдели пользовательские настройки от статуса аудита. На главной «AA» выглядит как подтверждённый уровень доступности, хотя он не проверен.
13. `src/styles.scss` содержит почти все стили приложения глобально; `app.scss` пуст. Масштабное обновление дизайна требует токенов, локальных стилей и ясных правил адаптации.
14. В `.github/workflows/deploy.yml` используется неверный флаг тестов `--run`. Покрытие сейчас ограничено тремя тестами оболочки, количества учебных элементов и изоляции двух жёстко заданных профилей.

## Требуемый пользовательский сценарий

### Первый визит

1. При открытии приложения, включая прямую ссылку на внутренний маршрут, сначала показывай полноэкранное приветствие. Учебный интерфейс не должен мелькать до определения активного профиля.
2. Шаг 1 — два отдельных обязательных поля **«Имя»** и **«Фамилия»**. Убери пробелы по краям; не принимай строку только из пробелов, слишком длинное значение и управляющие символы. Поддержи обычные имена с пробелом, дефисом, апострофом и разными алфавитами; не ограничивай ввод кириллицей. Покажи ошибки рядом с полем и фокусируй первое ошибочное поле после отправки.
3. Шаг 2 — выбор одной роли крупными карточками/radio: **«Спортсмен»**, **«Тренер»**, **«Ассистент»**. У каждой — короткое описание доступных сценариев. Есть кнопка «Назад» с сохранением введённого текста. Управление полностью доступно с клавиатуры.
4. Финальная кнопка — «Начать обучение» либо «Войти в деморежим» в зависимости от роли. Подпись рядом ясно говорит: данные хранятся только в этом браузере, пароль и настоящая авторизация отсутствуют.
5. Создай локальный профиль с постоянным UUID: `{ id, firstName, lastName, role, createdAt }`. Записывай его только после завершения обоих шагов. Не используй имя как ключ прогресса.
6. После завершения открой стартовую страницу роли. Если пользователь пришёл по внутренней ссылке, верни его на неё, когда эта страница доступна выбранной роли; иначе открой стартовую страницу роли. `returnUrl` должен быть только внутренним маршрутом приложения.

### Повторный визит и управление профилем

- При наличии корректного активного локального профиля пропускай приветствие и восстанавливай состояние после перезагрузки. Если localStorage недоступен, приложение должно работать хотя бы до закрытия вкладки и честно предупредить о несохранении данных.
- В шапке показывай реальное имя, фамилию и роль. Замени выпадающий список из четырёх заранее заданных людей понятным меню: «Сменить пользователя», «Добавить пользователя», при необходимости «Изменить роль». Смена пользователя не должна незаметно перезаписывать чужой прогресс.
- В одном браузере можно создать несколько локальных профилей; прогресс, лекция и попытки разделены по `id`. При выборе существующего профиля явно показывай, чей это профиль. Не называй это аутентификацией.
- Мигрируй старое состояние `adaptive-rowing-lms-state` без молчаливой потери прогресса: прежние встроенные персоны можно сохранить как помеченные демопрофили, но не входить под ними автоматически. Новый посетитель должен увидеть приветствие. Для повреждённого JSON предусмотрены безопасное восстановление и понятное сообщение.
- Форум хранится локально; новые сообщения подписываются введёнными именем и фамилией. Исторические демосообщения можно оставить с меткой «пример». При изменении имени существующие сообщения не должны неожиданно получить автора другого профиля.

### Ролевые возможности

| Роль      | Стартовая страница                                       | Действия                                                                                                                                                                              |
| --------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Спортсмен | Личный прогресс                                          | Изучает лекцию, отмечает страницы, проходит тест, видит свои результаты, использует форум и материалы.                                                                                |
| Тренер    | Панель тренера                                           | Видит **только локальные** профили спортсменов этого браузера, их результаты; управляет видимостью тем, сбрасывает локальные результаты с подтверждением, модерирует локальный форум. |
| Ассистент | Отдельный обзор для ассистента или явно read-only панель | Просматривает материалы, учебный маршрут и разрешённую локальную статистику; не может сбрасывать результаты, менять видимость тем или модерировать форум.                             |

Тренер и ассистент могут просматривать учебный контент без записи попыток за спортсмена. Не создавай видимость серверной защиты: клиентский выбор роли остаётся демонстрационным. Но интерфейс, маршруты и методы состояния должны последовательно соблюдать эти роли.

## Новый дизайн: изменить весь продукт, а не только главную

### Концепция

Создай узнаваемый интерфейс спортивной образовательной платформы: маршрут по воде, направляющие дорожки, ритм гребка и лаконичная пиктограмма весла. Визуально уйди от нынешней светлой универсальной сетки одинаковых карточек. Предлагаемое направление: глубокий синий `#102A3A`, светлый тёплый фон `#F4F5F0`, яркий бирюзовый `#1CAFA4`, коралловый акцент `#EC745C`, ясный тёмный текст. Это стартовые ориентиры; финальные цвета проверь на контраст. Используй 1–2 семейства шрифтов с локальным файлом или надёжным системным стеком, без обязательной загрузки внешнего CDN.

### Система интерфейса

- Определи токены цвета, типографики, отступов, радиусов, теней и состояний. Различай основные действия, вторичные действия, ссылки, уведомления, ошибки и статусы прогресса. Не обозначай состояние только цветом.
- Сохрани общую идентичность на приветствии, в шапке, курсе, лекции, тесте, результате, форуме, материалах, панелях ролей и настройках. Компоненты должны иметь согласованные заголовки, навигацию, пустые состояния и CTA.
- Нарисуй собственные простые SVG/ CSS-мотивы, связанные с греблей, и согласуй их с уже имеющимся `public/favicon.svg`. Не используй фиктивный видеоплеер, случайные фотографии и изображения без прав на использование.
- Приветствие сделай самостоятельным экраном с сильной композицией, кратким объяснением продукта, индикатором двух шагов и очевидной формой. На мобильном экране форма должна быть первой по порядку чтения.
- После входа шапка показывает активную роль и пользователя. Навигация адаптируется к роли; на узких экранах остаётся полностью доступной и не превращается в горизонтальную строку со скрытыми пунктами.
- Главный экран спортсмена должен сразу отвечать на вопросы «что уже сделано?» и «что делать дальше?». У лекции — заметная навигация по страницам и реальный прогресс. У теста — ясная структура вопросов и состояние попыток. У тренера — читаемая таблица/список, пустое состояние и честная подпись «профили этого браузера». У ассистента — свои полезные задачи, без тренерских кнопок.
- На страницах материалов показывай реальную доступность файлов. Отчёт о разработке и технический чек-лист не должны доминировать в основной навигации учебного продукта; перенеси их в раздел «О проекте»/служебную область, сохраняя доступ при необходимости.

### Адаптивность и доступность

- Проверь 320–375 px, планшет около 768 px и широкий экран 1280–1440 px. Не допускай горизонтальной прокрутки из-за шапки, таблиц, форм и карточек.
- Сохрани крупный шрифт, повышенный контраст и уменьшение анимации; учитывай `prefers-reduced-motion` и системный масштаб. Все интерактивные элементы имеют видимый фокус, достаточный размер цели, подписи и понятный порядок Tab.
- Для прогресса используй доступные текстовые значения и при необходимости `progressbar` с корректными атрибутами. Для ошибок формы обеспечь связь поля и сообщения. Проверь экран чтения для двух шагов входа и ключевых учебных сценариев.
- Проверь фактический контраст текста и управляющих элементов. Не заявляй WCAG AA без отдельной проверки.

## Техническая реализация

1. Создай отдельную область `onboarding` с двумя шагами, формой, роутом и guard для внутренних страниц. Сделай переход по маршруту реактивным; проверь прямые ссылки и перезагрузку.
2. Вынеси `LocalProfile`, роль и состояние хранения в отдельные модели. Версионируй формат localStorage и добавь проверку прочитанной структуры. Сохрани исходные учебные данные отдельно от пользовательских профилей.
3. Приведи маршруты и меню в соответствие с ролевой матрицей. Используй тип `Role` в guards вместо `string[]`. UI-проверки и методы сервиса должны совпадать по разрешённым действиям.
4. Исправь перечисленные функциональные дефекты: параметры лекции и темы, результат без попытки, фактическую видимость тем, форумную ссылку, несуществующий PDF и пути ресурсов для GitHub Pages.
5. Раздели глобальный `styles.scss` на дизайн-токены/общие примитивы и локальные стили компонентов там, где это улучшит сопровождение. Очисти неиспользуемые импорты и постепенно верни полезные правила ESLint. Не отключай проверки ради зелёного результата.
6. Обнови README и текстовые пояснения продукта под новый сценарий локальных профилей. Укажи ограничения деморежима и отсутствие синхронизации между устройствами.
7. Не добавляй Java/Node backend, базу данных, парольную форму или внешнюю авторизацию: этого нет в задаче и текущем окружении.

## Приёмка

- Первый запуск и прямая внутренняя ссылка открывают шаг ввода имени/фамилии, затем выбор роли; без обязательных данных вход невозможен.
- Созданный профиль сохраняется, повторный визит восстанавливает его, а смена локального пользователя не смешивает прогресс и попытки.
- Спортсмен проходит прежний курс с четырьмя страницами и пятью заданиями; порог 4/5 и лимит двух попыток сохранены.
- Тренер видит только локальные данные и действительно управляет видимостью тем. Ассистент не видит и не выполняет действия сброса и модерации.
- Невалидные маршруты и отсутствующая попытка дают понятный экран или перенаправление, не ошибку и не пустые значения.
- Ни одна видимая кнопка скачивания не ведёт на отсутствующий файл; локальные ресурсы работают с base href GitHub Pages.
- Все ключевые страницы получили новый согласованный дизайн на телефоне и десктопе; клавиатурная навигация, фокус и настройки доступности работают.
- `npm run lint`, `npm run format:check`, `npm test -- --watch=false`, `npm run build` завершаются успешно. Исправь CI: замени неподдерживаемый `npm test -- --run` на поддерживаемую команду. Добавь тесты для входа, восстановления/миграции, разделения профилей, ролей, маршрутов и оценивания.

## Порядок работы и отчёт

Сначала проверь актуальный `git status`, существующие изменения и сценарии. Затем разработай единый дизайн и модель локального профиля, реализуй сквозной вход, приведи страницы к новой системе, исправь найденные дефекты и выполни проверки. После каждого значимого этапа оставляй проект собираемым. В конце коротко перечисли, что изменено, что проверено командами и вручную, и какие ограничения прототипа сохраняются. Не объявляй задачу завершённой, пока критерии приёмки не выполнены.
